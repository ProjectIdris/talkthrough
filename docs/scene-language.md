# Scene language

The scene language is how the model answers: a small JSON document that says what to speak and what to draw, step by step. The overlay renders it with three.js. It is data only: nothing in a scene is ever run, evaluated or parsed as HTML.

It is written to be cheap for a fast model to emit and easy to stream: one step is a complete unit, and the first step can be drawn and spoken while the rest is still being written.

- Code: `src/scene/` (`spec.ts` is the table everything else is built from).
- JSON Schema for the model: `docs/scene.schema.json`, generated by `node scripts/build-schema.ts`.
- Examples: `samples/scenes/`.

## Shape

```json
{
  "steps": [
    {
      "say": "This chart shows revenue by quarter. The last bar is the tallest.",
      "actions": [
        { "op": "box", "id": "chart", "x": 80, "y": 180, "w": 480, "h": 440, "color": "blue" },
        { "op": "circle", "id": "peak", "x": 420, "y": 240, "w": 100, "h": 180, "color": "red", "at": 1.5 }
      ]
    }
  ]
}
```

A scene is `{ "steps": [...] }` (an optional `"v": 1` marks the version, an optional `"escalate"` hands the question on, see below). A step is `{ "say", "actions" }`. The renderer plays steps in order; a step starts when its speech starts, and each action starts `at` seconds later (default 0). Actions with the same `at` start in the order listed. A step ends when its speech and its last action have both finished.

Two layers are drawn:

- **Screen marks** are drawn flat over the screenshot: box, circle, underline, arrow, label, note cards and image cards, and tags pinned to parts of a 3D model.
- **The 3D model** floats over the page, lit and shadowed, and the user can drag it to rotate. It is built from a modelling vocabulary (shapes, surfaces, ready-made parts, copies) and moved with the same timed actions as everything else. The stage rectangle only says where it is fitted; there is no box around it unless `frame` is asked for.

Objects stay on screen until cleared. A follow-up question continues the same scene: ids from earlier answers can still be used, and a new answer starts by clearing only if it says so.

## Numbers and units

- **Screen coordinates** run 0 to 1000 across the screenshot, whatever its pixel size: `x` to the right, `y` down, `(0,0)` the top-left corner, `(1000,1000)` the bottom-right. The renderer maps them to the display.
- **3D coordinates** are in model units: `x` right, `y` up, `z` toward the viewer, origin at the middle of the stage. At zoom 1 the camera fits 12 units across the shorter side of the stage (a wide stage shows more to the sides, and a small model wants a `zoom`). It starts at `az` 0, `el` 15, looking at the origin. A solid is centred on its position. Angles are degrees. The origin of the model is where the shadow falls under it, on the page.
- **Time** is in seconds. `at` is the delay after the step starts (0 to 60). `dur` is how long a change takes (0 to 30, default 0.6). Things that appear fade in over a short fixed time.
- **Colour** is a name (`red orange yellow green teal blue purple pink white gray black`) or `#rgb` / `#rrggbb`. In the JSON Schema it is text. The validator reads another colour name (`gold`, `navy`, any CSS colour name) as the nearest palette colour and notes it; a hex colour is kept exactly, and a value that is neither a name nor a hex colour drops the action. Solids and parts may leave it out and take the colour of their surface.
- **Opacity** is 0 to 1.

No screen size is measured along both axes at once: every screen size is a width (`w`) or height (`h`) in its own axis units, so a shape that looks round on a 16:9 screenshot needs `w` smaller than `h` (about 9/16 of it). Text height (`size`) is in y units. A renderer maps each axis separately.

Out-of-range numbers are clamped by the validator, never rejected.

## Ids

Every mark and 3D object has an `id`: a letter followed by up to 31 letters, digits, `_` or `-`. Ids are unique across marks and 3D objects together. `all`, `marks` and `panel` are reserved. Actions that change or remove something name it by id, and an id that does not exist (yet, or any more) makes that action be dropped.

## Screen marks

Marks take `id`, `color` (cards, images and pins may leave it out: the look chooses) and optionally `at`.

| op | fields | |
|---|---|---|
| `box` | `x y w h` | rectangle outline; `x,y` is the top-left corner |
| `circle` | `x y w h` | circle or oval drawn inside the box (same fields as `box`) |
| `underline` | `x y w` | a line under text; `x,y` is the left end |
| `arrow` | `x1 y1 x2 y2` | from `x1,y1` to `x2,y2`; the head is at `x2,y2` |
| `label` | `x y text size?` | short text, up to 80 characters; `x,y` is the top-left corner; `size` is the text height in y units (10 to 100, default 24) |
| `card` | `x y w? title? rows? layout? to?` | a note card: a title and/or up to 6 rows of up to 60 characters; `w` is its width in x units (default 300); `layout` is `list` (default), `timeline` (rows written `when \| what`, laid along a line) or `stat` (the first row large); `to` is a screen point a curved line runs to from the card |
| `image` | `sx sy sw sh dx dy dw caption?` | a crop of the screenshot (region `sx,sy,sw,sh`) shown as a card at `dx,dy`, `dw` wide, with an optional caption; it needs the screenshot, so it is left out where the page has none |
| `pin` | `on point? text off?` | a tag pinned to the 3D object `on`: a dot at `point` (in the object's own space, default its middle), a leader line and the text; `off` is only a hint for the side the tag goes to (screen units from the dot); the renderer places tags itself so they keep off the model, each other and the page's text. It follows the object as it moves and goes when the object does |

## The 3D stage

`{ "op": "panel", "x", "y", "w", "h", "frame"?, "at"?, "dur"? }` places the stage as a rectangle on the screenshot: the model is fitted to it, and may reach past it. `frame` true draws a box behind the model; by default there is none. Sent again, it moves or resizes. If objects are added before any `panel`, the renderer uses a default rectangle.

### Surfaces

`material` is one of `plastic` (default), `metal`, `rubber`, `pcb`, `glass`, `glow`, `paper`. They are physically based surfaces lit by a room environment; `color` tints them, and an object with no colour takes the natural colour of its surface (a `pcb` is green, `rubber` near black). Solids and tubes have dark edge lines unless `edges` is false.

### Adding objects

`{ "op": "add", "shape": ..., "id": ... }` plus:

| shape | fields | |
|---|---|---|
| `box` `sphere` `cylinder` `cone` `torus` `plane` | `size` `pos`? `rot`? `color`? `material`? `bevel`? `edges`? `opacity`? | `size` is the bounding box `[x,y,z]`. A cylinder and a cone stand on `y` (diameter `x`, height `y`, cone apex up). A torus lies flat: outer diameter `x`, tube thickness `y`. A plane faces `+z` and ignores `z`. A sphere is an ellipsoid fitted to the box. A box is slightly rounded by default; `bevel` sets the rounding in units (0 for sharp) |
| `extrude` | `outline` `depth` `bevel`? `pos`? `rot`? `color`? `material`? | a flat outline `[[x,y],...]` (3 to 40 points, counter-clockwise, in the x,y plane) pushed out `depth` along `z` and centred on it: wings, fins, plates |
| `lathe` | `profile` `sides`? `pos`? `rot`? `color`? `material`? | a profile `[[radius,y],...]` spun round the `y` axis: bodies, nozzles, rings, bottles. `sides` (3 to 64, default 48) makes it faceted |
| `tube` | `pts` `radius` `flat`? `draw`? `color`? `material`? | a smooth tube through 2 to 24 points: cables, pipes, vessels. `flat` (0.05 to 1) squashes it to a ribbon whose wide side faces across the path. `draw` below 1 starts it part drawn |
| `line` `arrow` | `pts` `color`? `draw`? `opacity`? | a thin line through the points; an arrow ends in a head at the last point |
| `part` | `part` `size` `variant`? `n`? `pos`? `rot`? `color`? | a ready-made part fitted to the box `size`: `chip` (variant `black` or `metal`), `header` (`n` pins per row, two rows), `port` (variant `usb`, `usb3`, `ethernet`, `hdmi`, `usbc`; its opening faces `+z`), `lens` (axis `z`), `screen`, `button`, `fan` (`n` blades, axis `y`), `wheel` (`n` spokes, axis `z`) |
| `array` | `of` `count` `step`? `turn`? | `count` copies in all of the object `of` (with everything attached to it); the original is the first. Each copy is moved `step` and turned `turn` more than the last, about the origin of the group the original sits in: a row of pins, blades round a hub. The original joins the new group `id` |
| `text` | `text` `height` `pos`? `color` | text in the 3D scene, always facing the camera |
| `group` | `pos`? `rot`? | an empty node |

All take `parent`? (the id of a group, or of a part or shape, to attach to; they nest up to 6 deep, and a mark, a pin or a text cannot be a parent), `explode`? (see below) and `at`?. `pos` defaults to `[0,0,0]`, `rot` to `[0,0,0]`, `opacity` to 1. A child moves, turns and scales with its parent. To make something grow from its base, put it in a group at the base, offset the child by half its height, and scale the group (see `bar-chart.json`). Arrays are capped at 64 copies each and 400 in a scene.

`explode` is `[x,y,z]`, where the part goes when its group is exploded all the way (spread 1), in the units of the group it is in (capped at 100 either way). Without it a part moves outward from the group's origin. The same offset is where the part goes when the person opens the finished model with the Explode control (see the overlay notes); a part with none moves away from the middle of the parts around it instead. Give it where the real assembly comes apart (pins up, a shaft out the back); leave it off when outward is fine. The lean schema (`scene.schema.lean.json`, what the live models are asked for) leaves `explode` out, because every optional field there costs the model an explicit `null` on every part; the validator and the full schema accept it.

### The mechanism kit

Mechanism parts are ready-made `part`s for engines, gearboxes and pumps. Each is built from the same plain shapes a model could write, with good proportions, its own metal and finish (the object's `color` tints the main body), and named **anchors**: a `pin` with `anchor` lands on one by name (an unknown name falls back to the middle of the part). `size` is the box the part fits, centred on `pos`. Cylindrical parts have their axis along y (the crank, cam, gear and bearing along z), so a vertical engine's parts line up with no rotation.

| part | `size` and `n` | anchors |
|---|---|---|
| `cylinder-block` | `[x, y, z]`; the bore is round in x,z, 72% of the smaller side. Variant `cutaway` leaves the front half open so the bore and what moves in it show; `finned` adds `n` cooling fins | `bore-top`, `bore-bottom`, `front` |
| `piston` | `[diameter, height, diameter]`; crown, three rings, wrist pin | `crown`, `pin` |
| `connecting-rod` | `[width of the big end, length, thickness]`; small end up, big end down; centres of the two eyes are `big-end` (width/2 up from the bottom) and `small-end` (30% of the width down from the top) | `big-end`, `small-end` |
| `crankshaft` | `[x, y, z]`, axis z, `n` throws along it (default 1, spaced 360/n degrees apart); the throw radius is 30% of the smaller of x and y, so a crank-slider uses `radius` = 0.3 × min(x, y); at angle 0 the pin is at +y | `pin` (`pin1`, `pin2`... for several), `throw`, `axis-front`, `axis-rear` |
| `valve` | `[head diameter, length, head diameter]`; head down | `head`, `tip` |
| `camshaft` | `[lobe diameter, lobe diameter, length]`, axis z, `n` lobes (default 4), each with its nose at +y at angle 0 | `axis-front`, `axis-rear` |
| `spark-plug` | `[hex width, length, hex width]`; tip down | `tip`, `terminal` |
| `gear` | `[diameter, diameter, thickness]`, axis z, `n` teeth (default 16, 6 to 120) | `axis` |
| `spring` | `[diameter, length, diameter]`, `n` coils (default 8) | `top`, `bottom` |
| `bearing` | `[diameter, diameter, width]`, axis z, `n` balls (default 9) | `axis` |
| `pipe` | `[diameter, length, diameter]`, flanged ends | `top`, `bottom` |
| `elbow` | `[x, y, z]`: a 90 degree bend whose pipe diameter is z; one end opens downwards at the bottom right, the other to the left at the top | `a`, `b` |
| `housing` | `[x, y, z]`; variant `cutaway` leaves the front open to show the inside; bolts at the corners | `front`, `back` |

### Changing objects

All take `id` and optionally `at` and `dur`. These apply to 3D objects (`move`, `along`, `turn`, `scale`, `explode`, `reveal`) or to any object or mark (`style`, `highlight`). `style` and `highlight` on a group reach everything inside it.

| op | fields | |
|---|---|---|
| `move` | `to: [x,y,z]` | tween to an absolute position |
| `along` | `pts` | move along a smooth path through the points, ending on the last |
| `turn` | `to: [x,y,z]` | tween to absolute angles. The tween is linear, so from `[0,0,0]` to `[0,360,0]` is one full spin |
| `scale` | `to: [x,y,z]` | tween to absolute factors; 1 is the size it was added at |
| `explode` | `to` | spread the parts of a group outward from its origin: 0 assembled, 1 apart (up to 3). Build in the exploded state and tween to 0 to assemble |
| `reveal` | `to` | draw a tube, line or arrow on from its start: 1 is all of it |
| `style` | `color`? `opacity`? | tween colour and/or opacity; at least one is required |
| `highlight` | `color`? | pulse to draw the eye; the object returns to how it was |
| `cut` | `axis`? `to` | cut a 3D object, usually a whole model, open with a plane so the inside shows: everything on the front side of the plane (`axis` `x`, `y` or `z`, default `z`: the side facing the viewer) is removed and each cut face is capped like a solid section. `to` is where the plane is along that axis in the object's own space (0 is the middle of the object); it moves there over `dur`, and a later `cut` moves it on. `to` 100 is past everything, which takes the cut away. Parts that are open surfaces (a liner, a pipe wall) are not capped. The person's own Cut button cuts the whole model through the middle the same way |

### Machines

Parts that keep moving once started, in the x,y plane with the shafts along z (the kit's own layout). Put the parts of one machine in the same group. A machine stops when a group holding it is exploded, and when the user takes hold of the model; a finished scene leaves it running.

| op | fields | |
|---|---|---|
| `spin` | `id` `rpm`? `by`? `ratio`? `phase`? `axis`? `dur`? | turn a part about its own axis (`z` by default; `x` or `y` for others) at `rpm` turns a minute, negative the other way, 0 to stop; it gets up to speed over `dur` (default 0.8 s). Or `by` another part: this one then turns `ratio` times as far as that one (default 1; 0.5 half as fast, -1 a meshed gear) and `phase` degrees ahead, whatever the other part is doing. One of `rpm` or `by` is needed |
| `crank` | `id` `shaft` `rod`? `pin`? | `id` is a piston, `shaft` a crankshaft that is spinning: the piston slides along y as the crank pin goes round (the crank at 0 degrees has the pin straight up and the piston at the top), and the `rod` swings to join the pin to the piston. `pin` is which throw of a crankshaft with several (default 1). The rod's length, the crank's throw and the piston's pin come from the sizes of the parts |
| `cam` | `id` `by` `lift`? `open`? `phase`? | `id` is a valve (or any follower), `by` a camshaft that is spinning: the valve is pushed down by `lift` (default a fifth of its length) while the cam's total angle is within `open` degrees (default 110) of `phase` (default 180, the nose pointing down), with a smooth rise and fall. Set the camshaft's `rot` to fix its timing |
| `flash` | `id` `by` `angle` `span` `cycle`? | `id` is an object (a small sphere for a spark, a larger one for the burn) that is invisible except for `span` degrees from `angle` in each `cycle` (default 720) of the turning of `by`: it comes on quickly and dies away. For a four-stroke engine 0 degrees is the piston at the top starting the intake stroke, 360 the top of the compression, so the spark is at about 350 and the power stroke runs 360 to 540 |

A turning part's own `rot` stays as the scene set it, and the angle is added to it; this is exact when the other two angles are 0. A four-stroke engine: the crankshaft `spin` at 30 rpm, each camshaft `spin` `by` the crankshaft with `ratio` 0.5, an intake camshaft with `rot` `[0,0,135]` and an exhaust one with `rot` `[0,0,-135]` (each valve then opens as its cam's nose comes round to point down at it), a `crank` for each piston, and `flash` for the spark and the burn.

### Camera

| op | fields | |
|---|---|---|
| `orbit` | `az el` | place the camera on a sphere around what it looks at: `az` in degrees (0 faces the front), `el` the height angle (-89 to 89) |
| `zoom` | `to` | distance factor, 0.2 to 5: 1 is the default framing, 2 is twice as close |
| `focus` | `id`? | aim at a 3D object; without `id`, back to the origin |

The user can still drag to rotate; the next camera action tweens from wherever the camera is.

### Clearing

`{ "op": "clear", "target": ... }`: an id (the object and everything attached to it), or `all`, `marks` (every screen mark, card and pin) or `panel` (the stage and its objects, with the pins on them). A cleared id may be used again.

## When the user circled something

While the keys are held, a drag with the mouse draws a pen stroke on the display under the pointer (the overlay takes the mouse only for that time; clicks never reach the page beneath). If the stroke is more than a twitch, the model gets two pictures instead of one:

1. the whole screenshot with the stroke drawn on it in red, and
2. a closer, clean picture (no stroke) of the area around the stroke, cropped from the full-resolution capture, so small text and details stay readable.

The question text says that the circled area is what "this" or "here" means and gives the crop's position. **Coordinates do not change:** marks still run 0 to 1000 across the whole screenshot, never across the crop, so an answer can point at the circled thing with the same `box`, `arrow` or `label` as always. The red stroke is the person's, not part of the page, and is not described. With no stroke nothing changes: one picture, as before.

## Escalating

If the question is beyond the fast model (long research, deep reasoning, something it cannot see), it says so with a top-level `escalate`: a short reason, up to 160 characters.

```json
{ "steps": [], "escalate": "Finding the cause of this failure needs a deeper read of the log" }
```

It is allowed alongside steps (a brief partial answer is played, then the offer) or instead of them (`steps` empty). The app can then offer to pass the question to a slower, deeper backend, whose reply comes back in this same scene format. `escalate` is text only: it is cleaned like any text, cut to length, and dropped (the rest of the scene is kept) if it is not text or is empty. In strict structured-output mode it is a required nullable field, and models that are not escalating write `null`. `escalate` is last in the schema so it never delays the first step; the step stream exposes it as `stream.escalate` when it arrives, and `validateEscalate()` cleans it.

## What the validator does

`validateScene(raw, state)` and `validateStep(raw, state)` take what the model produced and return a clean scene made of fresh objects, plus a list of what they changed. They never run, import or interpret anything in the input; they read plain data fields only.

- A scene that is not an object with a `steps` list, or has another `v`, is refused (`ok: false`).
- An action with an unknown `op` or shape, a missing or wrongly typed field, a bad colour, an unknown or wrong-kind id, or a duplicate id is dropped; the rest of its step stays.
- A number outside its range is clamped. A value that is not a finite number drops the action.
- Fields the language does not define are removed. `null` means the same as leaving an optional field out (strict structured-output modes require that).
- Text loses control, zero-width and direction-override characters and line breaks, and is cut to its limit. Markup is not interpreted or removed: `<b>` is just the characters `<b>`.
- Steps, actions and objects past the limits are dropped.
- A step with nothing to say and nothing left to show is dropped.

A valid scene comes back deep-equal to what went in.

`SceneState` (`createSceneState()`) holds the ids so far. Keep one per session, pass it to every turn, and call `startTurn(state)` when a new question starts (`validateScene` does so itself) so the per-answer caps count from zero. A caller that streams with `validateStep` and forgets `startTurn` has every step after the 24th across questions dropped, with an issue that says so.

**The renderer's side of the contract:** draw every string as text (canvas, text geometry or `textContent`), never as HTML; never build code, URLs or file paths from scene fields; ignore anything that is not in this document.

## Streaming

`createStepStream()` takes the model's JSON text in chunks of any size (`push(chunk)`) and returns each step as soon as its closing brace arrives, ready for `validateStep`. Everything before the opening brace and after the closing one (code fences, chatter, even stray quotes) is ignored. It throws on mismatched brackets or a step that is not valid JSON, and `end()` throws if the text stopped early; steps already returned are still good.

**Pieces.** `createStepStream({ onPiece })` also reports, in order, each step's `say` text the moment its string closes, each action the moment its object closes, and then the step itself (`{type:'say'}`, `{type:'action'}`, `{type:'step'}`). A step is still the boundary; the pieces let a step be drawn while it is being written.

`beginLiveStep(state, { open(say), action(action) })` validates a step that way: `say(raw)` for the words, `action(raw)` for each action, `finish()` at the end of the step. Each action is checked on arrival, against the ids the scene already holds and under the same limits as a whole step (24 actions a step, the per-turn caps, id collisions), so what is drawn as it streams is exactly what `validateStep` would keep (`validateStep` is built on it). An action that names an object not seen yet (an array before the object it copies, a pin before its part) is held for up to six more actions, then dropped with its reason; an action that arrives before the words waits for them, and a step that never gets its words (missing, or not text) is dropped with them, streamed or whole. A step that repeats its `say` or `actions` key streams the first of each.

**Build order.** Because a streamed model appears part by part, the order the model writes it in is the order it is built on screen. The prompt guide asks for the order a person would assemble it: the base or frame first, then the main parts that rest on it, then moving parts, then small details, one sub-assembly per step, and an object before anything that refers to it (its group, its array, its move, its pin). `orderScore(steps, known)` reads a raw answer and says how much of it did: `refs` references to an object (a parent, the object a pin is on, the original an array copies, the object a move acts on), `early` of them to an object made only later, `missing` to one never made, and `score` the share in order (1 when every one comes after its object). It drops nothing; the app records it in each question's report.

## The JSON Schema

`docs/scene.schema.json` is plain JSON Schema (`type`, `properties`, `required`, `additionalProperties: false`, `items`, `enum`, `anyOf`, `$defs`/`$ref`). Every property is required and optional ones are nullable, so it fits the strict structured-output modes of providers that take JSON Schema; it uses no range, length, pattern or format keywords (ranges are in the descriptions and enforced by the validator). The root is `{ "steps": [...] }`.

For a model without structured output, the same schema is a good thing to put in the prompt, since the validator accepts the leaner form (optional fields left out).
